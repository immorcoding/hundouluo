# #27 UI 返工研究与 Astra 简报

- [#22 用户实机反馈](https://github.com/immorcoding/hundouluo/issues/22#issuecomment-5875526946) 称 bfe4a4d 原创画面“很不错”，并决定不用第三方开放美术包；[#22 完成评论](https://github.com/immorcoding/hundouluo/issues/22#issuecomment-5875643876) 确认该画面已合入。视觉锚点是本仓库的 [实际 Godot 战斗画面](../../docs/art/hangar-godot-combat.png)、[缺口画面](../../docs/art/hangar-godot-gap.png)，及作为构图参照、并非贴图的 [C 草图](../../docs/art/reference-c.png)。#22 的远景冷蓝层次、近景高密度装甲/支柱、琥珀警戒线和青白行动员／橙红机械兵的识别逻辑在 [#22 正文](https://github.com/immorcoding/hundouluo/issues/22) 与 [美术来源及制作边界](../../assets/art_source/README.md) 中可核对。这里的相对链接从本目录回到仓库根目录应使用 `../../`；如果 GitHub 查看器不能解析，直接见仓库 `docs/art/` 和 `assets/art_source/`。
- [当前 README](README.md) 已说明六图是暂停实际 `scenes/level.tscn` 后的关卡截图叠加评审 UI，并非接入后的实机 UI。六张 [预览](previews/) 和逐张 [未叠加捕获](captures/) 可一对一对照；[渲染脚本](render_previews.gd) 与 [源金属框](source/console-panel.png) 是可追踪制作源。以下诊断基于逐张以原生 640×360 查看这六图，以及脚本/场景的明确坐标，不把审美推断说成已被用户确认的具体替代方案。

## 不贴合之处：证据、判断、重做实验

| 部分 | 现有可复核事实 | 风格判断与可执行的试验（仍待用户看图） |
| --- | --- | --- |
| 字体 | [渲染脚本](render_previews.gd) 以 `SystemFont` 指定 `Microsoft YaHei`、请求 600 字重；HUD 标签 13px、数值/状态 11px，结算标题 27px、原因 15px、重试 14px。[HUD](previews/hud.png)、[失败](previews/death.png) 在 640×360 有连续平滑的无衬线字形，边框和地板则为硬边密集像素。[Godot SystemFont 文档](https://docs.godotengine.org/en/stable/classes/class_systemfont.html) 说明按系统字体名匹配并不保证字形/字重，缺席时回退。 | 用户已明确否定字体。首轮用**同一入包的简体中文字形**统一 HUD、任务失败/完成、死因和 R 提示；优先试 12px 原生像素字，标题只用 12px 的整数倍 24px，避免 11/13/15/27px 混用造成节奏破碎。关键标签/数字以至少 12px 原生画布试排；若密集汉字在 12px 反而费眼，则以有授权的清晰 CJK 字体作为备选，不盲目以“像素感”压过可读性。[Godot 字体指南](https://docs.godotengine.org/en/stable/tutorials/ui/gui_using_fonts.html) 要求像素字体 nearest、设计字号和控件整数倍、关闭子像素定位；小字 MSDF 可能不如传统栅格化清楚。 |
| 行动员生命 | [渲染脚本](render_previews.gd) 把三格画成 21×10、间隔 6px 的平直横条，另用 11px 的 `生命 3 / 3` 和第二个 `生命`/`危险` 标签重复表意；[3/3](previews/start.png) 与 [1/3](previews/low-health.png) 只能看到长度相同的抽象条/斜划。#22 的 [行动员](../../docs/art/hangar-godot-combat.png) 与甲板都由独立轮廓和多层金属形体构成。 | 把生命画成**三个可一眼数出的装甲/能量单元**，以 1–2px 硬边、嵌套暗槽、青色实芯及离散空槽体现同一机库工艺；1/3 仍留三格并用琥珀警戒角或状态词作冗余，不只改颜色。让 `3/3` 成为辅助读数，而不是两个“生命”标签和长条争夺视线。准备三种等规格实尺候选（装甲舱、硬边能量芯、警戒刻槽），放在同一真实场景 3/3 与 1/3 比较；不要默认心形或随意新玩法道具。 |
| 其他 HUD | 当前左板 `[12,12,174,52]`、右板 `[350,12,278,52]` 是 `StyleBoxFlat` 的纯深色圆角矩形、1px 单线与 2px 侧线；防御机甲使用 252×8 的连续琥珀条、十段 1px 刻线、三位数字。相比[已获认可的失败框](previews/death.png) 的铆钉、阶梯斜角、装甲压条，顶部两板几乎没有同源结构细节；[HUD](previews/hud.png) 显示顶部深色块占据显著宽度。 | 保留当前失败框的**装甲斜角、嵌边、少量铆钉/槽线**作为设计语法，不必把 348×174 框整体缩到 HUD。重绘两个较紧凑、像场景控制台的顶部模块，保留中央战斗视窗与 y≥64 的射线/地面。机甲条可在同一压槽内以 3–4px 高可计量能量芯加大轮廓做两种候选；数值和连续进度应一致，十段线不能使 1/120 错看为 0。青用于行动员、琥珀用于机甲/危险，余量暗色要仍可读。所有刻度/纹理用原生 640×360 整数像素绘制，不靠把 1774×887 原图缩成微小控制块。 |
| 结算其余部分 | [失败](previews/death.png)、[跌落](previews/fall.png)、[完成](previews/complete.png) 共同使用当前 `[146,76,348,174]` 金属框，但文字、顶沿彩线、内部分隔、扁平纯色 R 方块均由脚本另外画出；画面用 48% 深蓝全屏遮罩，背后的两个 HUD 在结算时仍显示并被压暗。 | **锁定失败框的主体轮廓和金属边缘为视觉参考**，但不要锁定内部字、字级、R 键帽、顶线、完成色或遮暗强度。让重试提示成为框内同语法的简短按钮/铭牌，保持真实的 `R 从关卡起点重试`，并以相同排版处理两种死亡原因和任务完成。重做完成版须与失败版并列审看，不可仅把标题从琥珀换成青色。结算后残留的顶部 HUD 是否保留，应通过两版合成图看层级，不改游戏状态机制。 |

注意：[当前脚本](render_previews.gd) 在 `start`/`fall` 不画机甲 HUD，其他状态画；但是否显示的正式条件是 [level.gd](../../scripts/level.gd) 中进入终点或机甲启用攻击后调用 `show_mech`。返工预览须遵循这一条件，并与 [正式 HUD 接口](../../scripts/level_hud.gd) 的生命、机甲、两种结算状态一致；本研究不授权改这些脚本。[项目画布配置](../../project.godot) 为 640×360 逻辑视口、1280×720 窗口与整数倍拉伸。

## 字体选择与许可核查（设计阶段候选，不代表已入包）

1. **优先试排：Fusion Pixel Font 12px `zh-Hans`、proportional。** [字体作者 README](https://github.com/TakWolf/fusion-pixel-font) 明列 8/10/12 像素、简体中文字形及等宽/比例模式，并建议一般排版优先比例模式；[作者的 OFL 文件](https://github.com/TakWolf/fusion-pixel-font/blob/master/LICENSE-OFL) 明示字体用 SIL OFL 1.1、构建程序另用 MIT。其 [官方发布页](https://github.com/TakWolf/fusion-pixel-font/releases/tag/2026.09.25) 有 12px proportional 的 OTF/TTF 发布包（以实际选择的 tag、文件、SHA256 锁定版本）。字体源以像素字为目标，适合先检验与 #22 硬边美术是否一致；作者自己提示拼接字源的语言特定字形有限，故要逐字审看本票的“行动员生命危险防御机甲任务失败完成跌落深渊从关卡起点重试”等字和 `R/0–9`。不建议凭网页预览判断 Godot 字距/基线。
2. **回退：Noto Sans CJK SC 的固定字重 OTF。** [Noto 官方字体库说明](https://github.com/notofonts/get-noto) 确认 Noto 字体以 OFL 1.1 发布并允许复制、修改、再分发；[官方 Noto CJK 项目](https://github.com/notofonts/noto-cjk) 提供 Sans 的简中版本。它不是像素字体；若 Fusion 的汉字难辨，可在同一 640×360 背景以清楚的 14–16px 标签/正文和受控 hinting 试排，避免为了像素感牺牲快速辨识。[Godot 字体指南](https://docs.godotengine.org/en/stable/tutorials/ui/gui_using_fonts.html) 说明字体导入、hinting、传统栅格和 fallback 设置。此方案是可测试备选，不能假定用户已接受其视觉。
3. **合法分发步骤。** 从字体作者官方 release/仓库获取未经修改的明确版本；记录文件名、tag/commit、下载 URL、SHA256 与使用范围；把**字体文件原样及对应版权声明、OFL 许可文本**与独立 UI 设计来源记录一起保存。正式工程入包/导出时复核许可证文件随游戏可被用户找到；如裁字、改字或转格式，按 OFL 对修改版、保留字体名和许可证的要求另核对，不把字体改以游戏根 `LICENSE` 授权。[SIL 官方 OFL 1.1 正文第 1–5 条](https://openfontlicense.org/open-font-license-official-text/) 允许嵌入软件但要求每份附版权与许可，禁止单独出售，修改版受保留字体名和同许可限制。目前 [现稿 README](README.md) 明言 `Microsoft YaHei` 仅来自 Windows 系统且**没有字体文件入包**；[Godot SystemFont](https://docs.godotengine.org/en/stable/classes/class_systemfont.html) 的平台回退也使它不能成为可复现交付依据。此处不是法律意见；最终具体包需逐文件复核。

## 真实画面验收矩阵与停止条件

以下是交付给 Astra 的**建议验收方法**，不是把视觉偏好伪装成自动测试。使用当前 [渲染脚本](render_previews.gd) 的实际关卡捕获机制或等价 Godot 渲染，保留源截图和合成图可一对一对照，不用纯概念背景、放大假 HUD 或仅设计工具画板。[#27 正文](https://github.com/immorcoding/hundouluo/issues/27) 要求三态 640×360 真场景；[现有验证记录](VALIDATION.md) 的尺寸与 y≥64 对比可沿用作防遮挡检查，但不能证明人的审美和动中可读性。

| 场景 | 必须一眼读出的信息 | 尺寸/画面检查 |
| --- | --- | --- |
| 普通游玩／缺口 `start` | 行动员 3/3；**无**防御机甲条 | 640×360 原图 100% 显示；在缺口边缘、黄色斜纹、弹丸和角色上无 UI 盖住。 |
| 终点激战 `hud` | 行动员 3/3、防御机甲有损生命与进度 | 同帧实机交火、明亮炮口和后方亮区仍能区分两组模块；数值与条长相符。 |
| 低生命 `low-health` | 仅余 1/3，另两单元清楚为空，危险不只靠颜色 | 与 3/3 并排，以 1 秒扫视判断；保留青/琥珀的角色分工，不造成机械兵/机甲威胁色误读。 |
| 受击死亡 `death`／跌落 `fall` | 两者任务失败同一已认可的外框；分别是“生命耗尽”“跌落深渊”；R 从起点重试 | 字/键帽与边框留白不挤压；两种背景仍识得是本关；不把失败外框的认可扩展为批准整张 UI。 |
| 击败机甲 `complete` | 防御机甲 0/总量、任务完成、R 重试 | 与失败并排看同源边框和有区分的状态色；不得出现矛盾的满格机甲条或只换标题颜色。 |

请另外截 `2/3`、机甲 `120/120`、`1/120`、`0/120` 的边界小样；在原生 640×360 **和整数 2× 1280×720** 两种窗口观察，不用浏览器缩放截图代替。请在静音实际移动/射击数秒期间真人观察：能否无需停下角色就读出生命与机甲状态；自动像素比对只证明未覆盖 y≥64，不证明真实可读。状态、画面尺寸、UI 与场景分层可以脚本检查；“像 #22”“看得舒服”必须交用户评审。若任何关键汉字缺字、粗细错位、生命 1/3 难辨、HUD 压住缺口/弹丸，先迭代再提交。现有状态仍为未批准，不关闭、不合并、不接入正式 UI。

## 交给 Astra 的最短执行简报

沿用失败页装甲金属外框作**唯一已肯定的 UI 元素**；重新设计全套中文字、三点生命、两侧 HUD、机甲进度、完成页内文及 R 提示。先用可合法分发的 `zh-Hans` 12px 像素字体与一款清晰 CJK 备选在真实 640×360 六态 A/B 试排，优先让三格生命的离散读数、机甲剩余与危险状态在静音交火时一眼明白。把 #22 已确认的冷蓝纵深、近景装甲斜角和稀疏青/琥珀指示沿用到 HUD，保持 y≥64 的战斗/缺口区域清晰；所有中文字和数值保留可编辑，来源/字体许可与版本可追溯。交付六态源捕获+新预览、字体字形核验、边界状态、真实窗口人工评审记录；仅修改独立 `prototypes/issue-27-ui/`，不接入正式场景，仍请用户批准。上述具体组件是设计实验，并非要求照抄现稿坐标或强制一款字体。
