# #27 经典动作游戏 UI 研究：先定信息与版式，再定材质

研究日期：2026-09-29。交付仅此文档；不修改设计图、游戏、议题标签。审阅对象是 `39cc2d2` 六态 640×360 预览，不是初稿。本研究提供下一轮方向，**不表示设计通过，也不是要求立即重画全部六态**。

## 结论与纠偏

优先试验“轻量战斗 HUD + 安静的结算排版”。当前最大问题不是金属不够像，而是只有少量信息却出现太多同等显眼的边框、重复读数与装饰。材质一致不能代替信息层级一致。用户最新意见明确说字体有所改善、金属框风格正确不等于全部 UI 都要套用；因此旧 [RESEARCH.md](RESEARCH.md) 中“锁定失败外框”“其余模块沿同源装甲结构”的建议不再作为强制设计条件。[最新人审](https://github.com/immorcoding/hundouluo/issues/27#issuecomment-5883330392)

沿用的项目事实是：三点行动员生命、终点防御机甲进度、死亡原因、任务完成、R 从关卡起点重试；信息青色、危险琥珀色；不添加武器库存、时间、积分或继续次数。#22 的认可对象是原创机库实机的空间层次与敌我识别，不是每个界面都必须模拟机库装甲。[#27 规格及完整讨论](https://github.com/immorcoding/hundouluo/issues/27)、[#22 已验收美术及讨论](https://github.com/immorcoding/hundouluo/issues/22)

## 资料范围与如何复核

采用 Nintendo 官方 SNES Classic 原版手册库中的 Konami、Capcom、Nintendo 手册。这是权利方/平台方正式提供的原版扫描，不依赖攻略网站重述。已实际渲染并看过下面列出的页面；页码同时给出印刷页与 PDF 页，避免封面造成偏移。手册页中的**游戏画面**才是 UI 证据，外面的出版物标题、标注箭头、纸页边框不是游戏 UI。[官方索引及版权列示](https://www.nintendo.co.jp/clvs/manuals/en_us/index.html)

比较用的百分比是从扫描页内游戏画面边界作的**视觉估算范围**，不是源资产像素测量，更不是原开发者公布的规范。扫描存在缩放、透视、印刷失真，不能据此声称原作使用精确几 px 字号。下文“字高占屏幕高度”指截图中字符可见高度；“占比”指控件包围盒，不是所有发亮像素的总量。640×360 数字另列为本项目试排约束，不将 4:3 截图拉伸成 16:9 模板。

## 四类经典布局：学习的是资源分配

### 1. Contra III：将常用信息缩成一小组，让战场保持连续

手册 p9 的单人横版画面把剩余人物、两种武器和炸弹集中在左上；图形与短数字直接叠在场景上，没有包住整组的厚金属外壳。该组约占画面宽度 40–50%、高度 10–13%，包围盒约 4–7% 面积；小字可见高度约屏幕高的 3–4%。组内紧凑、组外大面积连续场景，靠图形和固定位置建立读数，而不是每个数都带解释性标题。[手册 p9](https://www.nintendo.co.jp/clvs/manuals/common/pdf/CLV-P-SACCE.pdf#page=9)

死亡与继续是两个阶段：手册 p5 说明中弹/跌落会损失一个人物，全部用尽后才到 GAME OVER，再选择 CONTINUE；继续返回关卡起点。这里的“余命”不等于本项目“可受击三点生命”，不能照搬人物头像 ×3 导致误解。本项目应直接表示三次生命损耗；R 提示明确重试起点，不引入继续额度。[手册 p5](https://www.nintendo.co.jp/clvs/manuals/common/pdf/CLV-P-SACCE.pdf#page=5)

**可迁移的判断：** 单一行动员不需要“行动员 / 生命 / 3/3 / 三格”四层重复说明。试排时保留“生命”与三格，危险时才多一个明确提示。**不迁移：** 原作枪翼图、字形、双武器结构、余命与炸弹机制。透明叠字在本项目明亮机库上是否成立必须另测，不能仅凭此例删除全部背景衬底。

### 2. Mega Man X：细长计量器与复杂世界可以共存

手册 p12 的生命条沿左边上半部竖排；p13 特殊武器能量在其右侧增加一条。单条宽约屏幕宽 4–6%、高约 30–36%，双条组宽约 11–14%，两条合计包围盒仍约 4–5% 屏幕。分段填充和底部小标识承担识别，不额外写一整行“当前生命/最大生命”；中央动作空间连续。p14 暂停状态界面才把武器名称、库存和更多数值展开成整屏格局。[手册 p12–14](https://www.nintendo.co.jp/clvs/manuals/common/pdf/CLV-P-SABCE.pdf#page=12)

手册说明能量耗尽导致 X 爆炸，并在状态画面另列剩余生命；其能量与余命同样是不同概念。资料未直接展示结束画面，因此不能声称原作失败框是什么形状。[手册 p12、p14](https://www.nintendo.co.jp/clvs/manuals/common/pdf/CLV-P-SABCE.pdf#page=14)

**可迁移的判断：** HUD 按阅读任务裁减，不按背景材质复杂度等比例加装饰；机甲长条可以只留短名称与必要的计量轨。**不迁移：** 给三点生命硬套一根长竖条；它会侵入本项目左侧入场视野，且三格不需要这种细分精度。原作暂停屏的厚框更不能证明战斗 HUD 也应厚框。

### 3. Super Metroid：同一顶部带内分组，不靠同样的外框统一

手册“THE GAME SCREEN”把生命/能量罐置左，武器图标与库存放中，小地图置右。HUD 活跃带约为画面高度 12–15%，字高约 3–4%；组间有间隔，图标和数值上下对齐。地图需要自己的边界，数字并不因此都要加相同盒子。地图暂停画面则有大范围边框，承担另一种阅读任务。[印刷 p12–13，PDF p13–14](https://www.nintendo.co.jp/clvs/manuals/common/pdf/CLV-P-SAAHE.pdf#page=13)

手册明确能量归零意味着游戏结束，并在地图说明中标示最后保存位置；这是持续探索和保存结构，不能移植成本项目的“检查点复活”。没有直接证据支持本研究指定它的死亡字级或结局排版。[同手册 PDF p13–14](https://www.nintendo.co.jp/clvs/manuals/common/pdf/CLV-P-SAAHE.pdf#page=14)

**可迁移的判断：** 主生命和临时机甲信息可以共享基线、颜色规则、字级，外形无需同构；空白是分组工具。**不迁移：** 铺满整条顶部资源带、地图、能量罐、探索数字。本项目信息量远少于它，不能用“经典 HUD 常有很多数字”替现稿冗余辩护。

### 4. Super Mario World：透明信息带与局部强调

手册 Action Screen 的余命、收集数、时间与得分沿顶部排布，储备道具单独有框，其他信息直接叠在天空上。HUD 高度约 13–17%，字符可见高度约 3–4%，部分数字高于标签；组与组靠位置和空隙分开。唯一突出的储备框让可操作资源有形状锚点，不给每一组都做框。这里大面积明亮而低细节的天空是可读性的组成部分，不能忽略背景条件。[印刷 p6，PDF p7](https://www.nintendo.co.jp/clvs/manuals/common/pdf/CLV-P-SAAAE.pdf#page=7)

死亡说明将掉坑、受敌人伤害等归于损失人物；终点页展示中点与最终门绳的场景位置，完成首先有场景内目标。它的中点续关、计时和奖励不属于本项目；只能借鉴“保留行动结果的场景语境”，不能借其规则改 R 行为，也不能凭终点门截图推断 COURSE CLEAR 字体。[印刷 p7–8，PDF p8–9](https://www.nintendo.co.jp/clvs/manuals/common/pdf/CLV-P-SAAAE.pdf#page=8)

**可迁移的判断：** 只给必要对象一处强调；完成页可让已击败机甲仍被看见，失败页留出跌落位置的语境。**不迁移：** 彩色计分字、储备框造型、卡通图案，或把机库假定为同样干净的天空。

## 补充：死亡/完成空间关系的三张一手图

**Super Metroid，死亡后的可操作重试画面。** Nintendo Wii VC 官方说明页“リトライ”配有 256×192 的完整游戏图：黑底上方居中的 GAME OVER，下方小型目标图，中央任务提醒，再下面是上下两行 YES / NO；选项自身没有按钮外框，箭头标识当前选择。标题约在 y=35–45（画面高的 18–24%），选项约在 y=130–168（68–88%），两段职责分开；标题没有因“失败”而被放到极大，位置、空隙和亮字对暗底建立层级。原图的青色底部渐变负责选项区域氛围，不是厚重容器。本项目只需要一个 R 操作，借鉴这种分层顺序即可，不复制 YES/NO、任务图或退回标题入口。[官方说明及重试截图](https://www.nintendo.co.jp/wii/vc/vc_sme/vc_sme_04.html)、[可直接复核的官方原图](https://www.nintendo.co.jp/wii/vc/vc_sme/img/page_04/04_ph_d.gif)

**Super Mario World，GAME OVER 后的继续选择。** Nintendo Wii VC 官方说明配图在保留的世界地图上压暗主体区域，把“继续/结束”两项小字放于中央；外围地图框与地图语境仍可辨。它不是另造一张装甲对话框，也不是死亡瞬间。183×138 的低分辨率官网图足以判读位置和容器关系，不足以可靠测原生字号。启示是：失败后的操作可以非常小而明确；背景是否保留，是叙事/定位选择。本项目应保留失败关卡语境，用文字说明回到起点，不能从这张图迁入地图或读档流程。[官方说明](https://www.nintendo.co.jp/wii/vc/vc_smw/vc_smw_03.html)、[官方继续选择原图](https://www.nintendo.co.jp/wii/vc/vc_smw/img/page_03/03_ph_e.gif)

**Super Mario Bros. 3，关卡完成补充样本。** 官方原版日文手册印刷 p18/PDF p20 直接展示完成截图：上部居中结果行，稍下为获得卡片的一行说明和卡片图形；场景仍在，底部原有 HUD 保留，没有覆盖屏幕中央的大结果面板。结果/奖励两行包围盒约占截图宽 65%、高 20–25%，字高约 4–5% 屏幕高；扫描印刷精度有限，只作视觉估算。大片中下部负空间保留关卡收尾，强调来自文本与位置而非纹理。对本项目完成页的迁移是“任务完成 → 防御机甲已击败 → R 操作”三段，把庆祝/结果留给大字与场景，不凭空增加四节点完成轨。原作有卡片奖励，本项目没有，不能搬卡片框或奖励数值。[Nintendo 官方原版手册，PDF p20](https://www.nintendo.co.jp/clv/manuals/ja/pdf/CLV-P-HAACJ.pdf#page=20)

这些反例不意味着本项目必须黑屏或无框，而是证明：运行 HUD、失败操作、完成反馈可以采用不同的空间组织，仍然属于同一游戏。先决定玩家当时要读什么，再决定容器。A/B 两个项目方向的结算粗排因此应改变信息组合与轴线，而不是只换框颜色。

## 对当前六态的具体诊断

依据 [design_ui.gd](design_ui.gd) 的坐标与实际 [六态预览](previews/)。这些是本研究的视觉判断，不冒称用户逐项说过。当前稿的 12/24px 字与结算隐藏顶部 HUD 已解决部分旧稿问题；不要再把旧 RESEARCH 中“微软雅黑、结算残留 HUD”等诊断当作现状。

## 推荐方向、优先级和取舍

**A，首选：轻量顶部信息 + 文字主导结算。** 左上短“生命”与三格，右上仅在终点出现名称和细进度；需要时用小面积深色衬底/1px 阴影保障读数，不绘整块装甲机箱。死亡/完成用一个明确标题、一行原因/结果、一行 R 提示，保留背景场景；仅一条短强调线或一对角标。借鉴 Contra 的紧凑、Mario 的局部强调、Metroid 的固定分组；所有图形原创。收益是让真实机库主导画面；风险是亮区读字，必须同帧验证。首轮优先此方向，因为它直接检验“去掉统一金属框是否改善排版”。

**B，对照：薄仪表条 + 单层机库结算面板。** HUD 同样裁减，只给生命与进度各一条深色薄轨；结算可保留已认可的金属外框气质，但缩减边缘视觉重量，内部不再嵌徽记框、按钮框与分隔轨。标题/原因/操作用一根明确轴线。收益是保留用户曾肯定的材质感且改动易比较；风险是继续受旧外框尺寸束缚。因此不以“源图哈希相同”为设计验收条件，不默认框的现尺寸必须保持。

**C，备选：边缘生命列 + 横向机甲条。** 借 Mega Man X 的边缘计量，把三格沿左上竖列排列，其他读数仍靠顶部。可进一步减少横向占宽，但会增加左边垂直视野占用，且行动员三点生命不需要长竖条；暂不投入六态精修，只有 A/B 都被认为缺乏识别性时再试。

执行顺序：P0 正确状态、三点可数、死因/R 语义；P1 信息删减、字级与对齐、场景连续留白；P2 明暗与色彩对比；P3 外框材质、角标与纹理。首轮只做 A/B 各一张交火、一张失败、一张完成的**粗排对照**，相同截图/相同文字/同一字体，别把字体和风格同时全改而无法判断原因。用户确定方向后才补普通、低生命、跌落与边界精修。

## 640×360 可量化试排约束

以下是**本项目建议实验值**，不是经典游戏公布的规范或已通过的美术标准。需因字形实测微调并记录。

| 项目 | 首轮约束 | 为什么 / 如何验收 |
| --- | --- | --- |
| 安全边距与网格 | 四边至少 12px；基准 4px 间距；文字和轨道整数定位。 | 对齐统一但不强迫字间距等于网格。仍用 640×360 与精确 2× 看实尺。 |
| 战斗 HUD 总量 | 左生命包围盒 ≤128×32；右机甲 ≤208×32；两组总面积 ≤10,752px²，即 4.67%；首轮透明中央开口 ≥280px。 | 作为较现稿 10.07% 底板面积的明显减量试验；面积含空白不等于遮挡像素。HUD 必须 y<56，保持 y≥64 无覆盖。 |
| 生命 | 三格单格 16–20×10–12px，间距 4–6px；只设一个“生命”标签；不常驻“行动员”。 | 空格保留简单轮廓、填充清楚消失。1/3 保留“危险”或明确警示符号；是否保留辅助 1/3 由 A/B 决定，不用三种重复文本堆叠。 |
| 机甲 | 轨道宽 176–192px、可见填充高 5–7px；与名称间距 4–6px；数值预留至少 42px。 | 42/42 与旧 120/120 都试排，若保留精确数值不得挤压名称。1/max 至少 1px，0 必须空；不画无意义十段刻度。 |
| 字体 | 延续现有 Fusion Pixel 12px；常规 12px，结果标题 24px，最多两档。 | 用户只说“好一些”，不是最终认可。复杂汉字若实尺难认，另做一项字体试验，不用缩字塞框。nearest、整数设计倍数、关闭子像素遵循 [Godot 字体文档](https://docs.godotengine.org/en/stable/tutorials/ui/gui_using_fonts.html)。 |
| 对比与装饰 | 字与局部底色建议静态亮度对比 ≥4.5:1 作为检查目标；结构线亮度弱于正文，单组最多一处高亮装饰。 | 这是保守的内部读数目标，不宣称仅凭比值就满足游戏可访问性或运动可读性；亮区、暗区、炮口同时复核。 |
| A 结算内容 | 整组 ≤288×112px，中心 x=320；标题/原因/操作均沿同一居中轴或同一左边缘，不混用；标题到原因 12–16px，原因到操作 20–24px。 | 内容包围盒 ≤14% 屏；保留周围连续场景。文字组优先 y=124–236，按尸体/机甲位置再微调。 |
| B 结算容器 | 外轮廓试排 ≤320×144px，即 ≤20% 屏；文字离内边缘 ≥20px；单层容器。 | 与现稿 26.28% 对照，检验更安静的面板而非规定一定越小越好。不把旧框硬缩到字无法留白。 |
| 遮暗 | A/B 使用同一 30% 深色遮罩为起点，再与 40% 并排比较。 | 死亡与完成的角色/机甲状态仍能辨认。遮罩不是模糊背景，不用抹图制造留白。 |
| 结果语义 | 标题“任务失败/任务完成”；原因“生命耗尽/跌落深渊”或结果“防御机甲已击败”；最后“R 从关卡起点重试”。 | 标题最大、原因次之、操作清楚但不靠第二套厚边抢标题；不新增菜单/按钮行为/结算分数。 |

## 死亡/完成研究尚需补齐的证据与真人问题

四款手册与补充三图足以说明：生命、余命、继续、通关是不同信息，不能把任意 GAME OVER 模板贴到本项目；也足以反证“科幻场景复杂，所以所有 HUD 都要复杂装甲”。已用 Super Metroid 重试、Super Mario World 继续、Super Mario Bros. 3 完成图建立具体空间对照，但**Contra III、Mega Man X 的死亡/完成布局，以及另外两款的完整结局仍未量化**。若后续选择直接借鉴这些未覆盖画面，需补官方/合法原版录像或静帧，记录版本、直达来源、状态与时间点；不拿暂停菜单替代。这个缺口不阻止评审本项目 A/B 排版，却不能被省略成“四款所有结算状态已闭环”。

需要真人决定的是真正影响方向的问题：

1. A 的轻量信息是否仍有救援机库的气质，还是更偏好 B 保留单层金属结算？应看同场景并排图后选择，而非抽象问“喜欢什么风格”。
2. 三格配“生命”是否已足够直观，是否仍需要 3/3；机甲需要精确数值还是名称+进度即可？这些是信息取舍，不能被装饰设计自动决定。
3. 两种失败与完成的画面中，先看见的是结果、操作还是边框？希望留多少场景语境，现有 12px 中文在原生窗口是否能轻松读到？

验收用同一真实背景做 3/3、2/3、1/3 和机甲满/半/1/0；静音移动射击后让真人立即报告生命与机甲阶段，再看失败原因与重试位置。记录实际回答、误读对象和使用窗口，不把代理“看着清楚”或自动像素差检验当作人审通过。
